## 1 · What could run on the deploy

The deploy still has no settled step (`DP-01` still fails as expected, D-050),
so there was no dispute to restart around. Refunds are still switched off
(D-051). Probed live against `https://orizon-agents-be-stellar.onrender.com`:

| Probe | Answer | What it shows |
| --- | --- | --- |
| `GET /health` at 03:05Z, then ~04:00Z | `uptime_seconds` 1341.0, then 106.1 | Render restarted the service by itself within the hour. Restarts are routine, as the story says |
| `GET /api/agents/uat624_ext_op/binding` | `200`, `bound_at` 1790220347 (2026-09-24 03:25Z) | a binding written ~23 h before the running process started is still served, and bindings survive a restart only in Postgres |
| `GET /api/tasks/uat-603d-nonexistent/disputes` | `200`, empty window, `now` set | the per-task read is open: `TASK_AUTH_REQUIRED` is off, as in production |

| `GET /readiness` | `ready`; no store field | the store in use is not reported (D-063) |

**DU-05 on the deploy.** The startup log cannot be read from outside, and no
Render log access was available. Both stores are chosen from one variable,
`DATABASE_URL`, so the surviving binding is the deploy's own proof that it is
set: the dispute store is Postgres too. `tests/durability.spec.ts` asserts this
on every suite run. It fails if the binding is ever newer than the process, or
gone.

## 2 · The restart drill: a real backend on a real Postgres

Backend origin/main `3347090`, run as `uvicorn app.main:app --workers 1` (the
Render command) against PostgreSQL 17.6. Each restart is a hard kill, which is
what a spun-down instance gets, with no shutdown hook. Settlements were seeded
through the backend's own `PostgresDisputeStore.record_settlement`. Disputes
were opened over HTTP: challenge, a real ed25519 signature from a fresh payer
key, then `POST /api/disputes`. The drill is `tools/restart-drill/drill.py`.

| Scenario | Result | Verdict |
| --- | --- | --- |
| Open dispute, restart, `GET /api/disputes/{id}` | `200`, the record identical field for field: status `open`, reason (with `—`, `ï`, `😀`) byte for byte, `charged_usdc` and `creditable_usdc` 0.25, `opened_at` | Holds |
| Same, `GET /api/tasks/{id}/disputes` | disputes, settlement and `window_closes_at` identical | Holds |

## 3 · An unconfirmed refund, through the real uphold script

Dan was not available to reproduce a timed-out transfer on testnet, so the
path was driven locally. `scripts/uphold_dispute.py` ran live, not as a dry run,
against the same Postgres, with the refund switch on and a throwaway settler key.
The one substitution is the SAC transfer call, which answers
`{"status": "timeout", "hash": …}`: exactly what the Stellar client returns for a
submission it lost track of (`tools/restart-drill/run_uphold.py`). The dispute
service, the claim, the store and every line the script prints are real.

| Step | Result | Verdict |
| --- | --- | --- |
| Run 1, the transfer times out | exit **10**; one transfer signed; `THE TRANSFER TIMED OUT — IT MAY STILL LAND.` / `DO NOT RE-RUN THIS SCRIPT FOR THIS DISPUTE.` in a boxed banner; the in-flight hash and its explorer link; "look for a credit of about 0.2500000 USDC"; never "REFUSED" or "nothing was signed"; stderr has the `refund transfer unconfirmed and MAY STILL LAND — do not retry, reconcile by hand` ERROR line | Holds |
| The dispute afterwards, across a restart | `crediting`, `refund_tx` = the in-flight hash, `credited_usdc` null, no rating | Holds — correct behaviour, not a bug |
| `list_refund_claims()` | the dispute is there, oldest first, before and after the restart | Holds: the stuck payout can be found |
| Run 2, the script again | exit **6**; **no** transfer signed; `A CREDIT FOR THIS DISPUTE IS ALREADY IN FLIGHT.` / `DO NOT RE-RUN THIS SCRIPT FOR THIS DISPUTE.`; names `list_refund_claims()` | Holds |
| The hand-reconcile hint | "it SUCCEEDED" → `append_status(id, 'credited', refund_tx=<hash>, credited_usdc=<the amount the transfer moved>)`, "Read the amount off the explorer … without it the receipt can only show what was promised." Nothing about the rating | **Fails** (D-064) |
| The hint followed to the letter | the claim leaves the queue; the dispute is `credited` with its amount and **no rating**, and nothing will ever write one | **Fails** (D-064) |
| A later run on the reconciled dispute | signs no transfer, "ALREADY CREDITED — the credit will NOT be paid again", tries the rating (exit 12 here, with no ledger reachable) | This is the missing step, and the hint says the opposite: "Re-running this script instead would credit them a second time." |

The script's message on the timeout path is clear, and it says so twice:
headline and banner. The problem is only in what it tells the operator to do
after reconciling.

## 4 · The trace page, as the payer, across a restart

Frontend origin/main `e56a07a` under `next dev`, pointed at the drill's backend
on the same Postgres, in Chromium. Freighter is driven by a script that signs
with the payer's real key (SEP-53), so the dialog's signature is verified by the
backend for real. `tools/restart-drill/browser.spec.ts`.

| Scenario | What renders | Verdict |
| --- | --- | --- |
| Open dispute; restart; reload | "Under review", the reason, "Up to 0.25 USDC would be credited to your wallet if upheld", the receipt text identical before and after, and the closing `<time datetime>` unchanged | Holds |
| Settled workflow; restart; Dispute step 2 → reason → Sign and submit | accepted; the receipt shows "Under review" and the new reason | Holds |
| `crediting` dispute | badge **Refund in progress** (amber, pulsing); "The refund was submitted and is waiting for confirmation on Stellar; if it cannot be confirmed, the platform reconciles it by hand — you will not be paid twice, and will not be skipped."; credit "Up to 0.25 USDC to be credited to your wallet"; refund transfer "Submitted, waiting for confirmation" with the hash. Nowhere "Refunded", "Confirmed on Stellar", "Done:" or "credited to" | Holds |
| Reconciled by the hint | "Refunded"; "Done: you received 0.25 USDC; the dispute rating it costs Coder is not confirmed yet."; "Dispute rating against Coder — not recorded on-chain yet." This stays for good (D-064) | **Fails** (D-064) |
| `TASK_AUTH_REQUIRED=true`, restart, reload | the per-task read 404s; no receipt, no window, no dispute and no Dispute button; nothing tells the payer why. `GET /api/disputes/{id}` still answers `open` | **Fails** (D-065) |

After any restart the trace log itself is gone: the backend keeps traces in
memory. The page says "connection dropped — reconnecting" while the receipt
below it is whole. That split is by design (the settlement record keeps each
step's output summary for exactly this reason) and is noted, not filed.
