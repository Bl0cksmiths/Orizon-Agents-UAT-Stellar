# 6.03b evidence — the dispute refusal paths

Run 2026-09-24 against `https://orizons.xyz`. Testnet only.

> **Scope note.** The story arrived as a title only, so the refusal matrix below
> is QA's own reading of "the dispute refusal paths": everything the dispute API
> can refuse, split by whether a real settled dispute is needed to reach it.
> If the story's own criteria differ, the DR ids in `test-plan.md` are the place
> to correct them — the tests are written against observed behaviour, not
> against a guess about the wording.

## 1 · Refusals reachable today

These need no settlement, so they were exercised live and are asserted on every
suite run by `tests/dispute-refusals.spec.ts`.

| # | Refusal | Request | Answer |
| --- | --- | --- | --- |
| DR-01 | malformed job id | `POST /api/disputes/challenge` `{"job_id_hex":"nothex","step_index":0}` | `422 validation_error`, `string_pattern_mismatch` on `job_id_hex` |
| DR-01 | negative step index | same, `step_index: -1` | `422 validation_error`, `greater_than_equal` on `step_index` |
| DR-02 | forged nonce and signature | `POST /api/disputes` with `nonce` of zeros and `signature_b64: "AAAA"` | `404 unknown_job` |
| DR-03 | reason past the 500-char cap | `POST /api/disputes`, `reason` 501 chars | `422 validation_error` naming `reason` |
| DR-03 | payer that is not a G-address | `POST /api/disputes`, `payer: "not-a-wallet"` | `422 validation_error` naming `payer` |
| DR-03 | missing reason | `POST /api/disputes` without `reason` | `422 validation_error` naming `reason` |
| DR-04 | unknown dispute id | `GET /api/disputes/dsp_does_not_exist` | `404 unknown_dispute`, with a `request_id` and no traceback |
| DR-06 | adjudication without credentials | `POST /api/disputes/{id}/uphold` and `/reject` | refused — `503 dispute_refunds_disabled` today, `401 invalid_api_key` once refunds are on (covered by `DP-02`) |

**The ordering is right where it matters.** Opening a dispute with a forged
credential is refused as `unknown_job`, before any signature check, and the
response says nothing about signatures — a forger learns only that the job is
unknown. Validation errors come first of all, so a malformed body never reaches
the job lookup.

## 2 · Refusals that cannot be reached yet

Each of these needs a dispute that exists, which needs a settlement, which
needs a charge that lands (D-050, behind D-039). None was reachable on
2026-09-24.

| # | Refusal | Why it is unreachable | Expected behaviour to verify later |
| --- | --- | --- | --- |
| DR-05 | a wallet that is not the payer raises the dispute | no settled job to challenge | refused, and the reason names authorization rather than the job |
| DR-07 | the dispute window has closed | no window ever opens | refused as out-of-window, with the closing time stated |
| DR-08 | the same step is disputed twice | no first dispute can exist | `409` with the existing dispute id (`DuplicateDisputeResponse` is in the OpenAPI) |
| DR-09 | a dispute already upheld or rejected is adjudicated again | nothing to adjudicate | refused, and the first outcome stands |
| DR-10 | a challenge nonce is replayed | no challenge can be minted | refused, one use per nonce |
| DR-11 | the credit would exceed `max_refund_usdc` (default 1.0) | no refund can run | refused as `refund_above_cap`, nothing transferred |

`DR-05` is pinned in the suite with `test.fail()` and stands for this whole
family: today it fails at its own precondition — the challenge is refused
`unknown_job` because no run settles — and when it flips green the rest of this
table has to be walked by hand.

## 3 · What was not tested, deliberately

- **Rate limiting (`429`).** Every dispute route advertises it, and the deployed
  limiter is a whole-service bucket. Tripping it from a test would throttle the
  shared deployment for whoever else is using it, so it is left to a scheduled
  security pass rather than the functional suite.
- **`/api/payments/x402`.** The 6.03a story is explicit that it is a simulation
  stub and proves nothing; nothing here touches it.

## 4 · Acceptance criteria

| criterion | verdict |
| --- | --- |
| DR-01 validation refusals name the offending field | **Pass** |
| DR-02 a forged credential is refused without leaking that it was the credential | **Pass** |
| DR-03 an over-long reason, a bad payer and a missing reason are refused | **Pass** |
| DR-04 an unknown dispute id is refused cleanly and traceably | **Pass** |
| DR-05 a non-payer cannot dispute someone else's payment | **Blocked** — D-050; pinned |
| DR-06 adjudication is closed to anonymous callers | **Pass**, with the code ambiguous while refunds are off (D-051, D-052) |
| DR-07..DR-11 window, duplicate, re-adjudication, replay, refund cap | **Blocked** — D-050, D-051 |

No new defect was found in the reachable refusals: everything that can be
refused today is refused, with a named reason and no leakage. The gaps are the
two already-filed blockers, not new bugs.
