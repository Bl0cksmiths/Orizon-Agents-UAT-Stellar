# 6.03g evidence — the adjudication door and the refund switch

Run 2026-09-26. **No setting was changed on the deployed service.** Refunds are
off there, and they must stay off until the private money-path defect D-053 is
fixed. So instead of asking Dan to toggle them, the refunds-on half ran against
a real local backend. There is nothing to restore.

## 1 · On the deploy, refunds off

`tests/adjudication-door.spec.ts` against orizons.xyz (backend `08efeda`), 15
tests × 4 browser projects, 60 of 60 as expected at 17:15Z:

| Call (no operator key held by UAT) | Answer | Criterion |
| --- | --- | --- |
| `POST …/uphold`, `…/reject`, no key | 503 `dispute_refunds_disabled` | AD-01 |
| the same with a wrong key, the same key one character short, a latin-1 key (`kéy-ñ`), and the raw UTF-8 bytes of `kéy✓—🔑` | 503 `dispute_refunds_disabled` each time, and no 500 | AD-03 |
| no key, a well-formed wrong-shaped body (`{"note": 5, "extra": []}`) | 503, not 422 | AD-04 |
| no key, malformed JSON (`{not json`) on uphold | 503 | AD-04 |
| no key, malformed JSON on reject | **422 `json_invalid`**, the same with a wrong key | AD-04: **D-073** |
| `POST /api/disputes/challenge` and `POST /api/disputes`, no key | 404 `unknown_job` (no run settles, D-050), never `invalid_api_key` | AD-06 |

The refunds switch is checked before the key (D-052, filed as backend #69). So
while refunds are off, every caller gets the same 503 whatever key they send,
and the 401s can only be seen with refunds on (§2).

## 2 · On a real local backend, refunds on and off

`tools/adjudication-drill/drill.py` boots the backend `08efeda` under uvicorn,
as Render runs it, on PostgreSQL 17.6 with the 6.03e drill's testnet fixtures.
The disputes are real, opened with the buyer's real signature. "Nothing signed"
is read from testnet Horizon: the settler's account sequence number before and
after. Full run 2026-09-26: **68 passed, 1 expected failure (D-073), 0
failed**. No 500 in the output or the server logs.

**AD-01, the switch closes the route (pass).** Refunds off, with a valid
`API_KEY` configured and sent: uphold, and reject with a valid note, each
answered 503 `dispute_refunds_disabled`. The settler's sequence number was
20881383668842562 before and after. The dispute still read `open`, through
`GET /api/disputes/{id}` and in the store.

**AD-02, no boot without a key (pass).** Refunds on, with `API_KEY` unset and
set to `""` on testnet, and set to `""` on `mainnet`, `public` and `pubnet`
(mainnet passphrase, no signing key, so the switch alone forces the key). Each
time uvicorn exited 1 and never answered `/health`. Unset and empty print the
same words, and no configured value is printed:

```
app.config.ConfigurationError: Refusing to boot: 1 configuration problem(s).
  - API_KEY is required because DISPUTE_REFUNDS_ENABLED is on, so /api/disputes/{id}/uphold is a route that transfers the platform's own funds — whether or not the signer is wired yet. Without it every money-moving route is anonymous. Set API_KEY (in the Render dashboard for the deployed service) and send it as the X-API-Key header, or remove the credentials above to run a read-only/demo deployment.
```

A wording note, not filed: when the switch is the only cause, the last sentence
still says to "remove the credentials above", but none are named above it. The
real choices are to set `API_KEY` or to turn the switch off.

**AD-03, every bad key is a 401 (pass).** Refunds on, key configured. Six keys
were sent to uphold, and to reject with a valid note: none, wrong, the right key
minus its last character, `kéy✓-<key>` as raw UTF-8 bytes, `kéy-<key>` as
latin-1 bytes, and the right key plus a trailing latin-1 no-break space. All 12
answered **401 `invalid_api_key`**, and no 500. The bodies were identical apart
from the request id, so none reveals whether a key was sent. The sequence
number was unchanged and the dispute still read `open`.

**AD-04, the guard before the body.** Refunds on, no key. These answered 401,
not 422 (pass):
- uphold with `{"note": 5}`;
- uphold with `{not json`;
- reject with no body, with `{}`, and with `{"note": 5}`.

Reject with `{not json` answered **422 `json_invalid`**, not a 500, but ahead of
the guard: D-073, the same as live. Nothing was signed.

**AD-05, a rejection needs a reason (pass).** Valid key. Each attempt was
refused 422:
- no `note`: `validation_error`, missing;
- `null`: `validation_error`, string_type;
- `""`: `validation_error`, string_too_short;
- `"   \t\n"`: `rejection_reason_required`;
- `"\x00\x1b\x7f"`: `rejection_reason_required`.

After all five, the dispute still read `open` in the API and the store, and
nothing was signed. A real rejection with a reason then answered 200 `rejected`
and echoed the reason back.

**AD-06, the buyer needs no key (pass).** Refunds on, key configured. The
challenge answered 200 and the dispute opened 200 `open`, with only the payer's
wallet signature and no `X-API-Key`.

**D-074, beside AD-02.** With the mainnet passphrase, a signing key, refunds
off and `API_KEY` empty, `STELLAR_NETWORK=mainnet` refuses to boot, while
`STELLAR_NETWORK=pubnet` boots and serves `/health` (`drill.py d074`, XFAIL).
The refund door still holds under `pubnet` (AD-02). What slips through is the
general rule that a mainnet signer needs an operator key.
