and returns the custody, and no seal is ever written. A run with a `charged`
payout and a seal is not reachable from UAT today (D-NEW-RUN-1).

## 3 · Why no workflow on the deploy can complete

A step is paid only when its agent has an on-chain owner, and an agent is only
dispatched to through its bound endpoint. `GET /api/agents` on 2026-10-02 lists
six agents with `bound: true`, all with an on-chain owner. The backend's own
`GET /api/agents/{id}/readiness` probe of each one's endpoint:

| Agent | Price | Bound host | `reachable` |
| --- | --- | --- | --- |
| `algorex` | 0.01 | `testing.com` | failed — "answered 301, a redirect. Dispatches never follow redirects." |
| `Powerbot` | 0.12 | `powerbot.com` | done — a web page answers, but not the dispatch protocol: the 2026-10-01 run on it failed the same way (§4) |
| `3D_Artbot` | 50.0 | `arbot.com` | failed — "did not answer within 5 s" |
| `faulty_test_v2` | 0.2 | a Cloudflare quick tunnel | failed — hostname no longer resolves; also below the 5500 bps routing floor |
| `uat624_ext_op` | 0.01 | a Cloudflare quick tunnel | failed — hostname no longer resolves |
| `uat605_ext_op` | 0.01 | a Cloudflare quick tunnel | failed — hostname no longer resolves |

The agents the backend's own 5.01 team runs paid (`calculatorai`, `keyboardai`)
are no longer bound. The seeded `agt_*` agents have no on-chain owner, so the
tool refuses a plan that routes to them before signing: a settle could pay them
nothing. The settler's account on Horizon shows no paid settle since
2026-09-30; its only transactions since are UAT's released runs below.

UAT's own operator endpoint (`tools/operator-endpoint/server.ts`, as in 6.05)
could stand in, but it needs a public HTTPS tunnel to be dispatched to, and no
tunnel was available to this run. With one, the run is: bind
`uat624_ext_op` to the tunnel (owner-signed challenge), then run the tool with
an intent naming its skill (`haiku`, `uat624`).
