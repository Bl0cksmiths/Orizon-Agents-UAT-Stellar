## Defects

None drafted. The operator path behaved as specified throughout:
- registering, preflighting, binding and checking all worked;
- a valid public HTTPS URL was accepted;
- the planner routed to both bound, reachable, above-floor agents.

One observation, not a defect: the first readiness read of `qa607_ok` said
`reachable: failed`, "did not answer within 5 s". Around that time, tunnel A
took 2.3 to 4.6 s to answer a GET from this machine. The next read, about 30 s
later once the cache expired, said `done (200)`. The answer was accurate
against its own 5 s probe budget, so it does not disagree with the endpoint's
state. It does mean that a slow quick tunnel can make readiness flap while
dispatch, with its 100 s deadline, would still succeed. The browser stream
should allow for that latency on endpoint A.
