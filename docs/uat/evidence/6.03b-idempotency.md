## 2 · The seven attacks, in code

| # | Attack | Verdict | What guards it | What the loser sees |
| --- | --- | --- | --- | --- |
| 1 | Second dispute on a step | **Holds** | pre-check `dispute_svc.py:423-428`, store backstop `:459-466` | `409 duplicate_dispute`, body carries the full original dispute |
| 2a | Double-click submit | **Holds** | `useRef` in-flight flag set before the first await, `dispute-dialog.tsx:445-447`; button disabled while busy | nothing: one challenge, one wallet prompt, one POST, even for three clicks in one tick |
| 2b | Two tabs at once | **Holds** | same nonce → consumed once (`external_binding.py:494-502`); different nonces → Postgres partial unique index + `ON CONFLICT … DO NOTHING` (`dispute_store.py:244-245`, `:425-433`) | `400 challenge_expired` or `409 duplicate_dispute`; the UI then shows the original (gap: D-057) |
| 3 | Replay the signed body | **Holds** | nonce consumed on a verified signature, before any other check; 300 s TTL; bound to job and step | `400 challenge_expired` (message thinner than documented: D-056) |
| 4 | Re-uphold a credited dispute | **Holds** | returns the credit and retries the rating before any claim, `dispute_svc.py:1170-1182` | the same record and refund hash; no transfer signed |
| 5 | Two upholds at once | **Fails** | — | see D-053, held privately |
| 6 | Over the cap | **Holds at the default 1.0** | checked twice before signing, `refund_svc.py:227` and `:285-293`, on the exact amount sent | `refund_above_cap`, without the amount or cap (D-055); a non-finite cap disables it (D-054) |
| 7 | Two steps, one agent | **Holds** | rating id is `job_id[:8] ‖ sha256(job ‖ "orizon-dispute:v1" ‖ step)[:8]`; all 64 steps derive distinct ids sharing the job prefix | two ratings, neither a replay |

A ledger `Replay` answer is only ever handled on the rating path, which never
touches the refund claim or the transfer, so a replayed rating cannot cause a
refund to be re-signed.

Also found: without `DATABASE_URL` the in-memory store opens a second path to
paying one step twice (D-058, held privately). `scripts/prototype_refund.py`
calls the transfer directly, skipping the claim and the cap; ADR 0008 already
records it as not closed, and it needs the settler secret to run.

## 3 · Tests run

- Backend refund suites (`test_refund_claim`, `test_refund_execution`,
  `test_refund_svc`, `test_uphold_script`, `test_dispute_durability`): 130
  passed.
- Backend dispute suites (`test_dispute_api`, `_challenge`, `_store`, `_svc`,
  `_job_id`, `_rating_flow`, `_rating_submit`): 218 passed, 1 skipped (the
  missing-asyncpg path, unreachable because asyncpg is installed).
- Frontend dispute suites (`components/disputes`, `lib/disputes`,
  `lib/use-dispute-panel`): 410 passed; one timing test needs a 60 s timeout on
  this machine.

No real Postgres was available: every "Postgres" test runs against the repo's
`FakePool`, which emulates the SQL. **Real Postgres behaviour is unproven**,
including that it infers the partial unique index from the dispute conflict
target.

Coverage gaps: no backend test runs two upholds concurrently (which is how D-053
went unnoticed); none covers a non-finite cap; none asserts a verbatim replay is
answered `challenge_expired`; and the frontend's double-click test never clicks
twice in the same tick. The last was checked separately and holds.

## 4 · Acceptance criteria

| Criterion | Verdict |
| --- | --- |
| IB-01 No duplicate path produces a second transfer | **Fails in code** (D-053; D-058 without Postgres). Not run on-chain: no uphold is possible (D-051) |
| IB-02 A second dispute on a step returns the first | **Holds in code**, backend and frontend; D-057 is a gap when the refetch fails. Not run live (D-050) |
| IB-03 Re-upholding a credited dispute signs nothing | **Holds in code**, pinned by backend tests that fail if the guard goes. Not run live (D-050, D-051) |
| IB-04 One agent disputed twice on one job gets two ratings | **Holds in code**. Not looked up on Stellar Expert: no rating exists (D-050, D-051) |
| IB-05 The cap refuses before signing | **Holds at the default cap**; the refusal does not name amount or cap (D-055), and a non-finite cap fails open (D-054). Not run live (D-051) |

Nothing here is a pass by the card's own rule, which counts transfers on
Stellar Expert. What the code review settles is that IB-01 would fail if run
today, so switching refunds on (D-051) must wait for D-053.
