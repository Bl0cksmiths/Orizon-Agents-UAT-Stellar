## 3 · DS-04 — the reasons: who sees them, and no rejection without one

**No rejection without a reason (seed.py, through the adjudication route).**
`POST /api/disputes/{id}/reject` with no note answers
`422 validation_error`. With a note of only whitespace (`" \t\n "`) it answers
`422 rejection_reason_required`. After both, the dispute still reads `open`. The
real rejection then records the adjudicator's words as `rejection_reason`. The
uphold script refuses to reject at all.

**Nobody else sees either reason (FS-06, pass).** The credited and rejected
disputes were opened with another wallet (`GAAZI4TC…CWN7`) and with no wallet,
each in a fresh browser context. On all four pages:
- the receipt speaks of "the payer's wallet", never "your";
- there is no "Your reason" and no "Why it was rejected";
- neither the payer's reason nor the rejection reason appears in the rendered
  DOM, in the page source (the HTML as served for that URL), or in any response
  the browser received.

The backend withholds them itself: without a token or the operator key,
`/api/tasks/{id}/disputes` sends `reason: ""` and `rejection_reason: null`. The
trace page is client-rendered, so no dispute data is embedded in its source.

**The payer does see them, but only in the tab that ran the task (FS-05 pass,
FS-07 fail).** With the task's read token in the tab, the payer reads
"Why it was rejected" and the reason. With the payer's own wallet and no token,
the receipt reads "Rejected" and nothing more, over an empty "YOUR REASON"
heading. The wallet is never asked. That is D-067 (Major) and D-068 (Minor).

## 5 · DS-06 and DS-07 — phone width and screen reader, in the browser

**Phone (FS-11 pass, FS-15 fail).** At 360px with touch, a credited receipt had
no drawn element past the viewport's edge, and no hash box narrower than its
text. The page's `scrollWidth` was 360. Both 64-character hashes were visible,

`stellar.expert/explorer/testnet/tx/<hash>`. Each link measured 217×15px:
tappable, but under 24px (D-072). A real phone is still to be checked (§7).

**Screen reader, by its live regions (FS-09, FS-12 pass).**
- The countdown ("23h 40m left") changed on screen for 70 s with no text change
  in any live region. The countdown is not inside one: it is `aria-live="off"`.
- During the live uphold, the receipt's polite status region was given each
  sentence once, ending with "Your dispute against Researcher was refunded."
  No repeats.

This is the markup that decides what a screen reader says. Hearing it through
NVDA or VoiceOver is on the checklist (§7).

## 6 · Read in the code, not filed

A read-only audit of `components/disputes/*`, `lib/disputes.ts`,
`lib/use-dispute-panel.ts` and the backend dispute routes. Everything above was
then confirmed in the browser. These four notes were not, so they are recorded
here rather than filed:

- A pending rating that confirms changes the visible text, but not the live
  region's key (`status:status`). So the rating landing is not announced.
- A theoretical wrong tick: a timed-out rating hash that in fact failed, then a
  REPLAY on a later attempt, marks the first hash confirmed. It is rare, and
  needs three specific attempts in sequence.
- A 100-character unbroken agent name has no `break-words` in "Dispute rating
  against …". It would be clipped at 360px (the page hides horizontal overflow),
  not scrolled. Realistic names fit.
- The open state says what happens next, but not when a decision can be
  expected.

(00:19–00:33): each fails as pinned, on D-070, D-071 and D-072.
