criteria are PP-01..PP-08 in `../test-plan.md`. Production only:
`https://orizons.xyz`, frontend `main` at `049f3d52`.

`tests/guide-samples.spec.ts` and `tests/litepaper-formats.spec.ts`, run in
Chromium, WebKit and Firefox at desktop and phone widths. What only a real
phone or a screen reader can show is run from
`../checklists/6.11-devices-and-screen-readers.md`, and its results go in §4
below with the devices actually used.

## 2 · The guide's samples and the litepaper's formats (automated)

**PP-03, `tests/guide-samples.spec.ts`.** Three `verify="live"` samples,
copied with the page's own copy buttons and run with `bash -c` exactly as
copied, after the guide's own "Set the API base once" block: `network`,
`binding-read` and `readiness` (`AGENT_ID=uat624_ext_op`, a team agent). Each
returned exactly the documented keys, literals and placeholder types; readiness
returned all seven steps in order, with `ready` following the guide's rule. A
fifth test reads the binding of the unbound team agent `w1_audit_a7x` and gets
the documented `binding_not_found`. No mismatch between the guide and the API.

**PP-04, `tests/litepaper-formats.spec.ts`.** Each download is fetched from
the link `/litepaper` offers, and §6 is located by structure in each (heading
line, `h1#operations-and-governance`, the Word `Heading1`, the PDF's largest
type). Compared word by word against the Markdown's §6 (more than 4,000 words,
tables included, nothing excluded), the HTML, Word and PDF all match. Two PDF
print artefacts are allowed and explained in the spec: ordered-list numbers,
and the one web address that the print stylesheet prints a second time after
its link. The page's §6 link opens the HTML book with the §6 heading at the
top of the viewport.
