# 6.03c evidence — who may dispute, and when: window, wallet and challenge

Run 2026-09-24/25. Testnet only; no wallet signed anything and nothing was
submitted to the chain.

## 1 · What could run on the deploy

Every scenario in the card starts from a settled step, and none exists: `DP-01`
still fails as expected on 2026-09-25 (D-050, behind D-039). The one exception is
the reason, which the service checks before it looks the job up. Probed live
against `https://orizon-agents-be-stellar.onrender.com` with an unsettled job:

| Reason sent | Answer |
| --- | --- |
| `""` | `422 validation_error`, `string_too_short` on `reason` |
| `" \t\n "` | `422 reason_required`, message `"reason required"` |
| `"\u200b"` (one zero-width space) | `404 unknown_job` — the reason check passed (D-059) |
| 500 × `é` (1000 bytes) | `404 unknown_job` — inside the cap, which counts characters |
| 501 × `x` | `422 validation_error` on `reason` (`DR-03`) |

These are asserted on every suite run by `tests/dispute-eligibility.spec.ts`;
the two invisible-character cases are `test.fail()` pinned to D-059.

The window shortcut in the card (settle with `DISPUTE_WINDOW_SECONDS=120`) was
not used: it needs a settlement, and a Render setting change only the operator
can make.

## 2 · The backend, run locally

Backend origin/main `3347090` through FastAPI's test client on the in-memory
store, settlements seeded as the repo's own tests seed them, real Stellar
keypairs, the clock moved by patching. Repo suites `test_dispute_challenge`,
`test_dispute_svc`, `test_dispute_api`: 111 passed.

| Scenario | Answer on the wire | Verdict |
| --- | --- | --- |
| Inside the window | `200`, status `open` | Holds |
| Just after the close | `409 dispute_window_closed`, message `"dispute window closed"` — the closing time the service built is dropped (D-056) | **Partial** |
| Exactly at the close | accepted; refused 1 µs later — the window is inclusive | Holds |
| Setting changed after settlement | the close stamped by `_record_settlement` (`execution_svc.py:1067`) is kept; a shorter or longer setting moves nothing | Holds |
| Non-payer signs a valid challenge | `403 not_the_payer`, the same whichever payer they claim; the nonce survives for the real payer | Holds |
| Raw-bytes signature / SEP-53 signature | both `200`; a SEP-53 signature from a non-payer `403` | Holds |
| Spent nonce / expired nonce | both `400 challenge_expired` — distinct from `not_the_payer`, not from each other | Holds |
| Empty / whitespace-only reason | `422 validation_error` / `422 reason_required` | Holds |
| Reason of only invisible characters | `200`, dispute opened (D-059) | **Fails** |
| 500 characters, incl. 500 × 😀 (2000 bytes) | stored whole, byte for byte; 501 refused `422` | Holds |
| Reason containing a prompt-fence marker | stored altered and cut, 499 → 513 characters ending `[truncated]` (D-062) | **Fails** |
| Undelivered, uncharged step | `409 step_not_settled` for the payer; `403 not_the_payer` for anyone else | Holds |

A challenge can be minted by anyone and carries no payer; the task's disputes
view does show `settlement.payer`, which is documented as already public
on-chain.

## 3 · The frontend, run locally

Frontend origin/main `e56a07a`, the real receipt, dispute section and dialog,
with only the network and the wallet stubbed; the clock controlled by vitest
fake timers and Playwright `page.clock`. Repo suites: 410 unit tests and the
20-test `e2e/disputes.spec.ts` passed (the e2e needed a local config for this
machine's browser build and its slow first compile — environment, not product).

| Scenario | What renders | Verdict |
| --- | --- | --- |
| Countdown reaches zero, no dialog open | the row buttons and the credit terms go at the close on their own; "Dispute window closed"; no refetch | Holds |
| Countdown reaches zero, dialog open | the dialog stays, "Sign and submit" stays enabled, a signature is asked for, then `409` (D-060) | **Fails** |
| Non-payer connected | no button, no disabled control, no tooltip, no hint text, no dialog in the DOM | Holds |
| No wallet | the receipt, "Dispute window open … 20h left", "If you paid for this workflow, connect that wallet to dispute a step.", a Connect wallet button, nothing else | Holds |
| Empty reason | submit disabled for `""`, spaces, tabs and newlines, NBSP and U+3000; Ctrl+Enter sends nothing | Holds |
| 600 characters pasted | the field holds 500, "500 / 500 characters · limit reached", the POST carries 500 | Holds |
| 300 × 🙂 pasted | the field caps at 500 UTF-16 units (250 emoji, no split pair) — stricter than the backend's 500 characters, never looser | Holds |
| Undelivered step | no action; "Nothing was charged for this step, so there is nothing to dispute." | Holds |
| Expired vs wrong-wallet refusal | different text and different buttons | Holds |
| Reason refused as `validation_error` | generic "try again" with a retry button (D-061) | **Fails** (only reachable if the field's guards are bypassed) |

The payer is compared exactly, so a payer connecting through a muxed M-address
is treated as a stranger — consistent with the backend, noted rather than filed.

## 4 · Acceptance criteria

| Criterion | Verdict |
| --- | --- |
| WC-01 The window is enforced at both edges | **Fails** — both edges hold, but the refusal does not name when the window closed (D-056). Not run live (D-050) |
| WC-02 The UI withdraws the action when the window closes | **Fails** — the rows withdraw on their own; an open dialog does not (D-060). Not run live (D-050) |
| WC-03 Only the paying wallet can dispute | **Holds locally**, backend and frontend. Not run live (D-050) |
| WC-04 A spent or expired challenge is refused distinctly | **Holds locally** — `challenge_expired`, never `not_the_payer`; the service's fuller message is dropped (D-056). Not run live (D-050) |
| WC-05 A mandatory reason is enforced on both sides | **Fails** — empty and blank are refused live and disabled in the UI, but a reason of only invisible characters is accepted, live and locally (D-059) |
| WC-06 A reason is never silently trimmed | **Fails narrowly** — the cap holds on both sides and 500 characters are stored whole, but a reason containing a prompt-fence marker is stored altered and cut (D-062) |

## 5 · To run it on the deploy

1. The escrow fix (D-039), so a charge lands and `DP-01` passes.
2. A settled workflow with `DISPUTE_WINDOW_SECONDS=120` on Render, reset
   afterwards, for WC-01 and WC-02 with the page open; the close must be the one
   stamped at settlement.
3. Two wallets: the payer (Freighter, SEP-53) and a stranger, for WC-03 and
   WC-04, plus a signed raw-bytes attempt through the API.
4. A workflow with one failed step, for the undelivered-step check.

None of this needs refunds switched on, so D-051 and D-053 do not block it.
