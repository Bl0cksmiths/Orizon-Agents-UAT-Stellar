# 6.03c evidence — who may dispute, and when: window, wallet and challenge

Run 2026-09-24/25. Testnet only; no wallet signed anything and nothing was
submitted to the chain.

## 1 · What could run on the deploy

Every scenario in the card starts from a settled step, and none exists: `DP-01`
still fails as expected on 2026-09-25 (D-050, behind D-039). The one exception is
the reason, which the service checks before it looks the job up. Probed live
against `https://orizon-agents-be-stellar.onrender.com` with an unsettled job:

| Reason sent | Answer |
| --- | --- |
| `""` | `422 validation_error`, `string_too_short` on `reason` |
| `" \t\n "` | `422 reason_required`, message `"reason required"` |
| `"\u200b"` (one zero-width space) | `404 unknown_job` — the reason check passed (D-059) |
| 500 × `é` (1000 bytes) | `404 unknown_job` — inside the cap, which counts characters |
| 501 × `x` | `422 validation_error` on `reason` (`DR-03`) |

These are asserted on every suite run by `tests/dispute-eligibility.spec.ts`;
the two invisible-character cases are `test.fail()` pinned to D-059.

The window shortcut in the card (settle with `DISPUTE_WINDOW_SECONDS=120`) was
not used: it needs a settlement, and a Render setting change only the operator
can make.

## 2 · The backend, run locally

Backend origin/main `3347090` through FastAPI's test client on the in-memory
store, settlements seeded as the repo's own tests seed them, real Stellar
keypairs, the clock moved by patching. Repo suites `test_dispute_challenge`,
`test_dispute_svc`, `test_dispute_api`: 111 passed.

| Scenario | Answer on the wire | Verdict |
| --- | --- | --- |
| Inside the window | `200`, status `open` | Holds |
| Just after the close | `409 dispute_window_closed`, message `"dispute window closed"` — the closing time the service built is dropped (D-056) | **Partial** |
| Exactly at the close | accepted; refused 1 µs later — the window is inclusive | Holds |
| Setting changed after settlement | the close stamped by `_record_settlement` (`execution_svc.py:1067`) is kept; a shorter or longer setting moves nothing | Holds |
| Non-payer signs a valid challenge | `403 not_the_payer`, the same whichever payer they claim; the nonce survives for the real payer | Holds |
| Raw-bytes signature / SEP-53 signature | both `200`; a SEP-53 signature from a non-payer `403` | Holds |
| Spent nonce / expired nonce | both `400 challenge_expired` — distinct from `not_the_payer`, not from each other | Holds |
| Empty / whitespace-only reason | `422 validation_error` / `422 reason_required` | Holds |
| Reason of only invisible characters | `200`, dispute opened (D-059) | **Fails** |
| 500 characters, incl. 500 × 😀 (2000 bytes) | stored whole, byte for byte; 501 refused `422` | Holds |
| Reason containing a prompt-fence marker | stored altered and cut, 499 → 513 characters ending `[truncated]` (D-062) | **Fails** |
| Undelivered, uncharged step | `409 step_not_settled` for the payer; `403 not_the_payer` for anyone else | Holds |

A challenge can be minted by anyone and carries no payer; the task's disputes
view does show `settlement.payer`, which is documented as already public
on-chain.
