## 10 · Friction — what an operator would have to guess (for story 5.03)

None of these is a defect on its own; each cost time in this run or would cost
an outside operator more.

1. **The bind accepts two signature encodings; the dispatch uses only one.**
   The 2.04 runbook says *"sign `message` VERBATIM … (ed25519 → base64)"*
   without naming an encoding. Checked live after the restart: a raw ed25519
   signature over the message bytes was accepted (`200`, `replaced: true`,
   `bound_at 1789619066.97`, same URL), as was the SEP-53 one used for every
   earlier bind — `_signature_matches` deliberately takes both. The dispatch
   signature is SEP-53 **only**. An operator who learns "raw works" at bind time
   and verifies dispatches the same way rejects every genuine dispatch. The
   guide should say the two differ.
2. **Two hostnames for "Orizon".** The operator guide pins the signer from
   `https://orizon-agents-be-stellar.onrender.com/api/stellar/network`; the
   runbook, the UI and every bind call use `https://orizons.xyz`. Both answer
   today; an operator cannot tell which one is authoritative.
3. **The anonymous binding read drops the path but keeps the field name.**
   `GET /api/agents/{id}/binding` returned `"endpoint_url":
   "https://couples-experimental-saved-job.trycloudflare.com"` for a binding
   made to `…/dispatch`. It reads like a different, wrong binding. Name the
   field `endpoint_host`, or say so in the guide.
4. **No deadline to budget against.** The envelope has no `deadline_ms` (D-040);
   the only way to learn the ≈100 s budget was to hold a response and measure.
5. **"Connection refused" cannot happen to an operator behind a proxy.** With
   the tunnel up and the process down the backend got a proxy `502`; with the
   tunnel gone, a Cloudflare `530`. On `main` both classify as `error_status`,
   whose fix column says *"stop returning errors"* — the wrong advice for a
   crashed process. Only a directly exposed host produces `no_connection`. The
   guide's table should mention reverse proxies and tunnels.
6. **A partial run discards the output that did arrive.** In every failed case
   `seo.brief` delivered, yet the task's `artifact` was `null`. The buyer paid
   (in `spent`) for 0.009 of output they cannot retrieve.
7. **Every run ends with an error line.** `on-chain settlement failed` appears in
   successful runs too (D-039), so an operator skimming for red lines cannot
   tell a working run from a broken one.
8. **Routing is not predictable from the intent.** The same two-step request,
   phrased with the steps in the other order, produced a one-step plan
   (`pln_471ae51d`, only `uat605_ext_op`) — the other agent was dropped. An
   operator testing their own agent cannot force a known plan shape.
9. **`real: false` on a bound, on-chain, dispatched agent.** The marketplace
   listing for `uat605_ext_op` carries `"real": false` throughout the run. The
   field is undocumented, and "not real" is the wrong impression for the one
   agent in the run that was an external service.
10. **Reference agent not used.** This run's endpoint was the UAT capture server,
    not `Orizon-Agents-Example-Agent-Stellar`: the story needs the raw request
    and a switchable failure mode, which the reference agent does not provide.
    Whether its README works is story 6.06 and was not tested here.
