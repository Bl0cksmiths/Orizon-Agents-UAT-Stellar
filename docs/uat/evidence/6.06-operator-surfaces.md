## 4 · Friction — worked, but an outsider has to guess (for story 5.03)

1. **"Five commands" are three commands and two browser sessions.** Step 3
   (bind) is a browser page with a wallet, deliberately (*"Why there is no CLI"*),
   and step 2 is a hosting account. The table promises commands.
2. **Two hostnames.** The README's curls use
   `orizon-agents-be-stellar.onrender.com`; its links, and the dApp, use
   `orizons.xyz`. Both answer. Nothing says they are the same service.
3. **When to pin the signer is described three ways.** Step 1 prose says "pin the
   signer before you go live", *Getting paid* says it is "the key you pin in
   step 2", and `render.yaml` says "before you bind". Step 2 itself never
   mentions it.
4. **Which wallets can bind is not stated anywhere an operator reads first.** The
   README says "Freighter"; the picker offers six; two cannot sign messages
   (D-046).
5. **`price … per job` has no unit** on My Agents, where registration says
   USDC and testnet moves XLM.
6. **A failed settlement lookup prints `GET /stellar/settlement/{id} → 404 — Not
   Found`** to the operator. True, but it reads as "your agent is broken" rather
   than "our service is missing a route".
7. **The locked-wallet message says "click Register again"** on `/app/bind`
   (`wallet-errors.ts:217-224`, from source; checklist B confirms).
8. **The escrow note speaks for "any agent"** from one agent's payload (§3) —
   true today, but not something the page read.
9. **The dispatch deadline is documented only in the README.** The envelope
   carries no `deadline_ms` on the deployed build (D-040), so the README's
   *"less real time than the `deadline_ms` field suggests"* refers to a field an
   operator will not find.

## 11 · The earnings wording, observed after the redeploy (2026-09-24)

§3 recorded that the escrow note could not be reached on the pre-2.06 build.
After the backend was redeployed the settlement lookup succeeds
(`{"total_stroops":0,"entries":[],"unavailable":null}`) and the panel renders
the zero state for real. What an operator now reads under Settlement:

> **⚑ No payment has settled to `<agent>`.** The escrow recorded no charge
> against this agent in the last 7 days. That window is the whole of the log we
> can read — Soroban RPC keeps 7 days of contract events and drops everything
> older — so this is a statement about the last 7 days, not about the agent's
> whole history.
>
> **Why nothing settles** — The escrow's charge path cannot move a customer's
> funds… That transfer fails without failing the run — the run still finalizes
> as complete — so a finished job can leave no payment behind, and the job log
> and the money disagree… This is a defect in the escrow contract, on the
> platform's side of the line. It is not a measure of your agent, and not a
> signal about demand for it.

**Verdict: honest, and it matches what the chain says.** The 2026-09-24 re-run
produced seven authorizations and zero `charged` events (6.05 §13.4), which is
exactly what this panel claims. It is not filed as a defect, as the story
directs. The one overreach noted in §3 stands: *"the readable event window holds
no charge from a customer for any agent"* is hard-coded rather than read, and is
shown from a single agent's payload.

Pinned by `OS-07 where the money would be, the dashboard names the escrow defect
instead of a zero` — the `test.fail()` marker is removed, and the test asserts
the wording live. OS-07's remaining defects are unchanged on this build: the
`online` badge on an unbound agent (D-044) and the contradictory routable note
(D-045) both still reproduce.
