# 6.07 evidence — EP-04, reclaiming an authorization that never ran

EP-04: *Given an authorization that was never executed, when it expires and the
payer reclaims from the console, then the full held amount returns to the
payer, and the console offered the reclaim.* Reclaim had never been exercised
live before this run.

## 0 · What the code says, before the run

Read at FE `0c8a10b7`, BE `9aa6fca`, contracts `origin/main`.

- **Contract** `reclaim(payer, auth_id)`: payer auth; `Unauthorized`(1) for
  another wallet, then `Replay`(7) if settled, `Revoked`(6) if reclaimed,
  `Locked`(9) while `ledger.timestamp() <= expires_at`. It sets `revoked`,
  transfers the whole `max_amount` from the escrow to the payer, and emits
  `reclaimd` with `(auth_id, payer, returned)`.
- **Backend** `POST /api/stellar/build/reclaim` runs
  `authorization_guard.check_reclaimable` first, a read-only simulate that
  signs nothing: 403 `authorization_payer_mismatch` for another wallet, 409
  `authorization_spent` for a settled **or** reclaimed one (the message says
  which), 409 `authorization_locked` until the wall clock is 10 s past
  `expires_at`. Only then does it build the unsigned XDR.
- **Frontend.** The plan card authorizes and executes behind one button. When
  the authorization confirms but `/api/orchestrator/execute` fails, the card
  shows "The authorization confirmed, but the run was not started" and the
  `EscrowHeldNotice` with its `ReclaimControl`. The control says "Reclaim opens
  at … (in about N minutes)" until `expires_at`, tells any other wallet "Only
  the paying wallet can reclaim", and otherwise offers "Reclaim … ▸".
- **Where the held authorization lives.** On the plan card it is React state
  only. `rememberHeldAuthorization(task_id, …)` writes sessionStorage
  `orizon.held-authorizations` only after `execute` returns a task id, so an
  authorization whose execute never answered is never written there. The trace
  receipt's reclaim needs both that entry and a failed settlement, so it cannot
  apply either. A reload, a closed tab or a fresh session loses the offer.

## 1 · How the drill reaches "authorized, never executed"

`tools/escrow-reclaim-drill/reclaim.spec.ts`, one worker, serial, one browser
page for the whole run:

1. The buyer builds a plan on orizons.xyz and presses Authorize. The dApp's own
   code builds, signs (through the Freighter shim, with the real QA buyer key)
   and submits the authorize transaction.
2. The only interception in the drill: `page.route` aborts the one request to
   `/api/orchestrator/execute`, as a dropped connection would. The escrow, the
   chain, the authorize build and submit are untouched; the backend never sees
   an execute, so no run starts and no release is attempted.
3. Custody is checked on chain: the `authd` event and the `authorization` view.
4. Before expiry: the console's countdown, the route's `authorization_locked`,
   and another wallet's refusal.
5. The same page stays open past `expires_at`, because the plan card's state is
   the only place the console holds the offer (§0). The drill then reclaims
   from the console's own control and checks the chain.
6. After the reclaim: a second reclaim, an execute with the reclaimed
   authorization, and a settled authorization from the EP-02 run, each through
   the backend's own routes.

## 2 · Drafted defects

### D-NEW-RECLAIM-1 — the reclaim route's refusal codes are not the ones the console reads (Minor)

- **Criterion.** EP-04: "Given an authorization that was never executed, when
  it expires and the payer reclaims from the console, then the full held amount
  returns to the payer, and the console offered the reclaim."
- **Steps.** `POST /api/stellar/build/reclaim` with the settled authorization
  `00000000000000000000000000000009` (payer `GB4K6…AYKK`, settled by
  `0ada07084b5aa1c196fb8e45b15d3712dcbefaf320a315a84e8cf2ab7adc556b`; the
  drill re-reads `settled=true` on chain first).
- **Expected.** 409 `authorization_settled`, as the route's own docstring says
  and as the console's `lib/reclaim.ts` maps to "Nothing to reclaim: a
  settlement already took this authorization over…". Likewise
  `authorization_revoked` for a reclaimed one.
- **Actual.** 409 `authorization_spent` for both, with the reason only in the
  message ("this authorization was already settled — anything unspent was
  returned"). The console does not know that code, so it says "The reclaim did
  not go through. The reclaim could not be prepared: …" and keeps the Reclaim
  button. That is reachable on the plan card whenever the execute request
  failed without an answer but the run did start and settle — the very case
  the held-funds notice warns about.
- **Test.** `reclaim.spec.ts` › "a settled authorization is refused with the
  code the console reads" (`test.fail`). Signs nothing.

### D-NEW-RECLAIM-2 — the console's reclaim offer does not outlive the tab (draft, browser test owed)

Found by reading the code (§0) and to be confirmed in the browser run: an
authorization whose execute never answered is held only in the plan card's
React state. A reload, a closed tab or a fresh session offers no reclaim
anywhere in the console, and the "Reclaim without the console" values vanish
with it. Severity to be set from the browser run; Major is expected, since the
payer can then recover the funds only by finding the authorization id on an
explorer and calling the contract by hand.
